# 11 — Security Findings (running log, initial pass)

Findings below are from source actually reviewed so far (auth + role/permission pass). This is a running log per the handoff's Section 42 test requirements — add to it as more source is reviewed, don't replace.

## F1 — `route:list` fails: missing controller class
- **File:** `routes/addon.php` (included from `routes/admin.php` via `include('addon.php')`)
- **Broken routes:** `GET /addon/install/exam` and `POST /addon/install/exam`, both pointing at `App\Http\Controllers\Admin\Addon\AddonInstallExamController`.
- **Confirmed via:** live error log (`storage/logs/laravel-2026-08-24.log`), repeated `ReflectionException: Class ... does not exist`, recurring across multiple timestamps same day — this isn't a one-off, it's a standing broken state in the checked-out copy.
- **Impact:** blocks `php artisan route:list` entirely, which blocks any tooling (including this audit) that needs a full route dump. Also means these two admin routes 500 if hit.
- **SchoolOS action:** Section 42 already requires an automated "all routes resolve, all controllers exist" test — this is the concrete motivating case for it.

## F2 — Unauthenticated cache-clear endpoint
- **File:** `routes/web.php` line 41–43
- **Route:** `GET /cache-clear` → `Artisan::call('cache:clear')`
- **No middleware at all** on this route — it sits outside any `Route::group(['middleware' => ...])` block, unlike the `/payment/subscription` route two lines above it which is correctly wrapped in `['middleware' => ['siteadmin']]`.
- **Impact:** any unauthenticated visitor can trigger a full application cache clear. Low-severity (no data exposure) but real — repeated hits could be used for a denial-of-service-style cache-thrash, and it signals an inconsistent pattern (some routes in this file are protected, this one was overlooked).
- **SchoolOS action:** no admin/debug routes should ever be reachable without an explicit middleware group; this should be a lint rule / CI check, not just code review discipline.

## F3 — Superadmin school-scope bypass is enforced by scattered conditionals, not structurally
- **File:** `app/Traits/AuthenticatesUsers.php` (partial — line 71 comment, line 86 code, seen via grep only)
- **Pattern:** `if ($users->usergroup_id == 1) { /* bypass school check */ }`
- **Impact:** this may be entirely intentional (a platform superadmin legitimately needs cross-school access), but the bypass is implemented as a manually-repeated `usergroup_id == 1` check rather than a structural exemption (e.g., a global scope that superadmin queries are built to skip). Every place tenant-scoping is enforced needs the same bypass condition remembered and applied consistently — one omission is a cross-tenant access bug, not just a superadmin convenience gap.
- **SchoolOS action:** tenant scoping should be enforced by a single mechanism (e.g., a scoped repository/global query scope) with an explicit, centrally-defined superadmin exemption — never a per-call-site conditional.

## F4 — Client-supplied `usergroup` on OTP/password-reset flow — CONFIRMED, full chain traced
- **Files:** `app/Http/Requests/API/OTPRequest.php`, `ResetPasswordRequest.php`, `ResetChangePasswordRequest.php`, `app/Http/Controllers/Api/UserController.php` (`resetPassword`, `storePassword`, `checkReset`, `resetChangePassword`)
- **Confirmed via real source (`app.7z`), not grep.** The three-step password-reset flow is: `resetPassword` (send OTP) → `storePassword` (verify OTP, uses `OTPRequest`) → `resetChangePassword` (consume verified OTP, write new password). All four methods, independently, resolve the target user the same way:
  ```php
  User::where('mobile_no', $request->mobile_no)->where('usergroup_id', $request->usergroup)->first()
  ```
  `usergroup` is validated only as `'required'` in every request class — never checked against an enum, never re-derived from an authenticated session (this flow is pre-auth by design, that part's fine). **Contrast confirmed:** the parallel teacher/parent login requests (`LoginRequest.php`, `TeacherLoginRequest.php`) hardcode `usergroup_id` server-side (7 and 5) instead of trusting request input — this reset flow is the one place in the app that doesn't.
- **Severity, now bounded by actually reading the flow:** every step still requires possession of the OTP token itself (delivered out-of-band via SMS to the phone tied to `mobile_no`), so an attacker who only guesses `usergroup` (a fully known, small integer range — see `03-role-permission-map.md` §1) cannot complete an account takeover from that alone. The realistic purpose of `usergroup` here is disambiguating a phone number shared across multiple accounts in different roles (e.g. a staff member who is also a registered parent) — a plausible legitimate need, not obviously malicious design. **Downgraded from "unconfirmed severity" to "confirmed low-to-moderate": not an auth bypass, but see the two new findings below (F16, F17) that this same trace surfaced.**
- **SchoolOS action (unchanged, now evidence-backed):** the reset-password flow should resolve identity from something the user proves (the mobile number + a delivered OTP), never from a second client-supplied field used as a raw disambiguator with no validation against what the account actually is. If SchoolOS needs to support one phone number mapping to multiple role-accounts, that mapping should be resolved server-side (e.g., "this number matches 2 accounts, which one?" derived from an authenticated lookup) — not accepted as a bare client parameter with no relationship check to the requester.

## F16 — Uncaught `\Error` in password-reset flow: `catch(Exception $e)` doesn't catch null-property access
- **Files:** `ResetPasswordRequest::messages()`, and the general pattern across `Api\UserController`'s reset-flow methods.
- **Root cause:** `ResetPasswordRequest`'s `check_mobile_no` validator correctly returns `false` when no user matches `mobile_no`+`usergroup` — this is a real, working guard. But when it fails, Laravel still calls `messages()` to build the validation error text, and `messages()` unconditionally does `$user->userprofile->status` on `$this->user`, which is `null` in exactly this case. Dereferencing a property on `null` in PHP 8 throws `\Error` (`Attempt to read property "status" on null`), not an `\Exception`. Every surrounding `try/catch` in this controller (`resetPassword`, `storePassword`, `checkReset`, `resetChangePassword`) is written as `catch(Exception $e)`, which does **not** catch `\Error` — `\Error` and `\Exception` are siblings under `\Throwable`, not related by inheritance.
- **Impact:** submitting a `mobile_no`/`usergroup` combination that matches no user — the exact case the validator was built to reject gracefully — produces an uncaught fatal error instead of the intended "Mobile Number Is Not Registered" message. This is a confirmed crash (readable directly from the code, not a "needs live repro" case like F5/F6), and it's reachable by any unauthenticated client hitting the password-reset endpoint with an arbitrary phone number.
- **Also relevant:** no rate limiting is visible anywhere in `ResetPasswordRequest`, `OTPRequest`, or `ResetChangePasswordRequest` — combined with the crash above, an unauthenticated actor can repeatedly probe arbitrary `(mobile_no, usergroup)` pairs against this endpoint, either to fatal it repeatedly or (for real pairs) to trigger repeated OTP SMS sends to a victim's phone (SMS-bombing), with nothing in the reviewed code to slow that down.
- **SchoolOS action:** (a) catch `\Throwable`, not `\Exception`, at any boundary meant to convert internal failures into clean API responses — or better, validate/null-check before dereferencing rather than relying on try/catch as the safety net; (b) rate-limit any endpoint that triggers an SMS/OTP send, keyed by both the target identifier and the caller's IP.

## F17 — Stock Keeper role: authorization scaffolding exists, implementation does not
- **Files:** `app/Http/Controllers/Auth/LoginController.php` (docblock), `app/Traits/AuthenticatesUsers.php`, `app/Http/Middleware/RedirectIfAuthenticated.php`, absence of `app/Http/Controllers/Stock/DashboardController.php`
- **Confirmed via real source:** `LoginController`'s docblock claims "Stock Keeper (ID 12) → /stock/dashboard," but `$redirectTo` is a hardcoded string, `AuthenticatesUsers::authenticated()` (the intended hook for this) is an empty stub, and `RedirectIfAuthenticated` sends every authenticated user to `/admin/dashboard` unconditionally. There is no `Stock/DashboardController.php` anywhere in `app/Http/Controllers`, unlike every other role. Combined with `routes/stock.php` being 0 lines (`04-route-map.md`) and `MustBeStockKeeper` being the only stock-related file in `app/`, this role has an authorization identity (`usergroup_id`, middleware alias) but no actual application behind it.
- **Impact:** low as a security issue (nothing is reachable that shouldn't be — quite the opposite, nothing is reachable at all), but relevant to SchoolOS scoping: this is not a role to "preserve behavior" from, since there is no behavior.
- **SchoolOS action:** treat Stock Keeper as a role requiring net-new design, not migration from GegoK12 — there's no reference implementation to extract requirements from beyond "it should exist as a role."

## F18 — Teacher-facing authorization gates check tenant only, never class/subject assignment — CONFIRMED, single most significant authorization finding in the audit
- **Files:** `app/Providers/AuthServiceProvider.php` (`Gate::define('member', ...)`, `Gate::define('academic', ...)`, `Gate::define('homework', ...)`, `Gate::define('document', ...)`); consumed by `Teacher\StudentDetailsController::show()` / `showDetails()` / a third method (all three call sites), `Teacher\HomeWorkController` (line 334), `Teacher\AssignmentController` (line 331), and the corresponding `Teacher\Approval\HomeWorkController` (line 403) / `Teacher\Approval\AssignmentController` (line 399).
- **Root cause:** every one of these Gate closures has the identical shape — `return $user->school_id == $member->school_id;` (and the equivalent for `academic`/`homework`/`document`). This checks tenant membership only. None of them query `class_teacher_links` (model `Teacherlink` — `school_id`, `academic_year_id`, `standardLink_id`, `subject_id`, `teacher_id`) to confirm the requesting teacher is actually assigned to the class/section/subject the target student, homework, or assignment belongs to.
- **Impact:** any teacher can view the full record (`StudentDetailsController::show`, 310-line profile including attendance, fees, discipline, documents, exam marks, siblings) of **any student in the same school**, not just students in classes they're assigned to teach — and can view/act on **any** homework or assignment record school-wide via the same pattern, including inside the `Approval/*` sub-privilege controllers, which are meant to gate teacher-on-teacher approval, not just teacher-on-student access. `class_teacher_links` exists, is populated, and is used correctly elsewhere (lesson plans, timetable) — it is simply never consulted at the authorization boundary. This is a real, structural over-broad-access defect confirmed directly from source, not a hypothetical.
- **SchoolOS action:** the "Scope" concept must query the assignment table directly as part of the authorization check itself — school-level tenant match is necessary but not sufficient for any endpoint that returns a specific student/homework/assignment record. See `12-schoolos-architecture.md` §3a for the concrete design response.

## F5 — Registration-number login very likely crashes (not just fails)
- **File:** `app/Traits/AuthenticatesUsers.php`, `validateLogin()`
- **Root cause:** `username()` dynamically resolves the login field to `email` or `registration_number` depending on input shape, but the `checkactive` and `checkexit` validators are hardcoded to look the user up by `'email'` regardless of which field was actually resolved. For a registration-number login, that lookup returns `null`, and the immediate next line (`$users->userprofile->status != 'inactive'`) dereferences a property on `null`.
- **Impact:** a fatal PHP error (not a validation message) on what looks like an intentionally-supported login path — the whole reason `username()` exists is to support login via registration number, so this isn't a rare edge case, it's a documented feature that appears broken as written. **Needs a live login attempt with a registration number to confirm** (static reading strongly suggests a crash, but the exact runtime behavior — e.g. whether Laravel's error handling downgrades this to a generic 500 vs. something else — should be verified before treating it as fully confirmed).
- **SchoolOS action:** the credential-resolution field must be threaded consistently through every validator in the chain, and "user not found" must be a normal failed-validation outcome, never a null-dereference.

## F6 — `checkschool` validator can resolve the wrong user via a non-unique field
- **File:** same trait, `checkschool` validator
- **Root cause:** the lookup is `User::orWhere('email', ...)->orWhere('mobile_no', ...)->orWhere('name', ...)->orWhere('registration_number', ...)->first()` — `name` is included as a match field. Names aren't unique identifiers.
- **Impact:** if a submitted "email" string happens to match another user's `name` field (plausible collision, e.g. a school where a display name looks like an email-ish string, or just an unlucky match), the school-active check runs against the wrong user's school. Best case this causes a confusing false rejection; worst case it could let the check pass using a different user's `school_id` than the one actually authenticating. **Severity unconfirmed without a live repro** — flagging as a design smell that needs a deliberate look, not a proven exploit.
- **SchoolOS action:** login lookups should only ever match on genuinely unique, credential-appropriate fields — never `name`.

## F7 — Global session + impersonation middleware apply to every request, including API
- **File:** `app/Http/Kernel.php`
- **Detail:** `StartSession` and `Nckg\Impersonate\Impersonate` both sit in the top-level `$middleware` array rather than the `web` group, so they run unconditionally on every request in the application, API included. This is likely intentional (it's what lets Sanctum's stateful-request middleware work at all), but it's undocumented as a deliberate choice anywhere in the code — it reads like something that happened while debugging Sanctum and was never revisited.
- **Impact:** low on its own, but worth confirming the impersonation middleware genuinely no-ops cheaply when not impersonating, since it's now unconditional per-request cost. Not a vulnerability by itself — logged for completeness per Section 42's "authentication: session expiration / token authentication" test coverage requirement.

## F8 — Duplicate role-gating mechanisms at the middleware layer
- **File:** `app/Http/Kernel.php`
- **Detail:** 13 hand-written `MustBe*` middleware classes coexist with Laratrust's generic, parameterized `role`/`permission`/`ability` middleware. This is the middleware-layer instance of the same duplication already flagged at the model layer in `03-role-permission-map.md` (System A vs. System B). Not a security bug per se, but it means "which mechanism gates this route" must be checked per-route rather than assumed, which is exactly the kind of ambiguity that produces authorization bugs over time (a route protected by the "wrong" or an incomplete mechanism could be missed in review).
- **SchoolOS action:** one parameterized role/permission middleware, no per-role middleware classes.

## F9 — Specialized `User` subclasses don't enforce their own type — cross-role data leak risk
- **Files:** `App\Models\Users\StudentUser`, `TeacherUser`, `ParentUser`
- **Root cause:** none of these classes apply a global scope restricting queries to their own `usergroup_id`. Type-correctness is left to individual scope methods remembering to add `->where('usergroup_id', N)` by hand, and most don't: **zero** of `StudentUser`'s three scopes and **zero** of `TeacherUser`'s four scopes filter by usergroup at all; `ParentUser` is inconsistent (6 of 9 scopes filter correctly, 3 don't).
- **Impact:** any code calling e.g. `StudentUser::byAdmissionNumber(...)` or `TeacherUser::byQualification(...)` queries the full `users` table with no role restriction, despite the class name strongly implying otherwise. This can return the wrong user type (a teacher instead of a student, etc.) to a caller that has no reason to suspect it, wherever these particular scopes are used. **Severity depends on where these scopes are actually called from** — needs the calling controllers to assess real-world impact — but the pattern itself is a confirmed defect, not a hypothetical.
- **SchoolOS action:** enforce type constraints via one global scope per specialized subclass, applied once at the class level — never rely on each new scope method to remember it.

## F10 — No web route group for parents at all
- **File:** `app/Providers/RouteServiceProvider.php`
- **Detail:** every other role (student, teacher, librarian, receptionist, accountant, stock keeper, superadmin) has a dedicated `map*Routes()` method wiring up a URL prefix, middleware stack, and controller namespace. There is **no `mapParentRoutes()`** — no `/parent` prefix exists anywhere in the provider, despite `Kernel.php` defining a `'parent' => MustBeParent::class` middleware alias that this provider never references.
- **Impact:** this is the handoff's own Section 0 observation, now confirmed at the exact mechanism level rather than inferred. Most likely explanation: parents are intentionally mobile/API-only (consistent with the dedicated parent API login endpoints already found) and were never meant to have a web dashboard — a legitimate design choice, not necessarily a defect. Flagging because SchoolOS needs to make this an explicit decision rather than an accidental gap.

## F11 — Error-suppressed route include
- **File:** `routes/api.php` line 3 — `@include('teacherapi.php');`
- **Detail:** the `@` operator suppresses PHP warnings/errors from the include itself. Contrast with `admin.php`'s unsuppressed `include('addon.php')`, which is exactly why the missing `AddonInstallExamController` class (F1) surfaced loudly in logs. Using suppression on a routes-file include is a fragile pattern — it could mask a missing/renamed file at boot time in a way that fails silently rather than loudly.
- **SchoolOS action:** never suppress errors around route registration; a missing route file should fail loudly at boot, not silently.

## F12 — Shared URL prefix, two different authorization rules
- **File:** `RouteServiceProvider::mapAccountantRoutes()` / `mapPayrollRoutes()`
- **Detail:** both `accountant.php` and `payroll.php` are registered under the same `/accountant` prefix, but gated by two different middleware (`accountant` vs. `adminaccountant`). A future route added to the wrong file would inherit the wrong authorization rule with no signal from the URL shape that anything was off.
- **SchoolOS action:** one URL prefix should correspond to exactly one authorization boundary.

## F13 — No unique constraint preventing duplicate attendance records — CONFIRMED at both schema and application layers
- **File:** `database/migrations/2020_04_06_131754_create_attendances_table.php`; application layer confirmed via `app/Traits/AcademicProcess.php::createAttendance()` and `app/Http/Requests/AttendanceAddRequest.php` (both web and API/Teacher variants). Full trace in `09-attendance-map.md`.
- **Detail:** the `attendances` table has no unique index on `(user_id, date, session)`. **Now confirmed (previously "not yet reviewed"):** application code does attempt duplicate prevention, via a `check_session` validator that checks `Attendance::where([school_id, academic_year_id, date, session, standardLink_id])->exists()` before allowing a `store()` to proceed. But this is a plain check-then-act query with no locking and no transaction wrapping the check itself — a genuine TOCTOU race between two concurrent submissions for the same class/date/session — and it operates at **class+date+session granularity**, not the `(user_id, date, session)` granularity the schema gap actually concerns. The write loop itself (`createAttendance`) does zero duplicate-checking — it's a bare `new Attendance; ->save()` per student with no query beforehand.
- **Additional confirmed finding:** because `check_session` blocks *any* second submission for a class/date/session outright, and no `update`/`correct`/`edit` method exists anywhere in the attendance domain (`Teacher`, `Admin`, or `Api\Teacher` `AttendanceController`s — all three fully reviewed), there is currently **no way to correct a mistaken attendance entry** through the application at all. This isn't just a missing audit trail (as originally flagged) — it's a missing capability, full stop.
- **Impact:** duplicate-prevention is explicitly required by the handoff's own Section 42 test list. The application-layer guard reduces but does not eliminate the risk (race condition still open), and provides no correction path even for legitimate mistakes.
- **SchoolOS action (unchanged, now more specific):** enforce the unique constraint at schema level as `(user_id, date, session)`, not class-level — this is also what unblocks building a real correction flow, since a class-level lock (as GegoK12 has) makes per-student correction structurally impossible without redesigning the guard first.

## F14 — Medical/health data stored in the general student-academic-enrollment table
- **File:** `database/migrations/2020_02_18_053405_create_student_academics_table.php`
- **Detail:** `student_academics` — the table that tracks a student's yearly academic enrollment (roll number, class, academic status) — also directly stores medical fields: medication problems, medication needs, medication allergies, food allergies, other allergies, other medical information, height, weight.
- **Impact:** these are two very different sensitivity classes of data sharing one table and therefore one access-control surface — anyone able to read a student's enrollment record can read their medical information, with no ability to apply separate, stricter access rules to the sensitive half.
- **SchoolOS action:** split health/medical fields into their own table with independent access policy, separate from academic enrollment records.

## F15 — Misleading table name: `student_history` is not enrollment history
- **File:** `database/migrations/2021_03_31_070442_create_student_history_table.php`
- **Detail:** the table name strongly implies student academic/enrollment history, but its actual columns (`read_at`, `entity_id`/`entity_type` polymorphic pair, `type` enum of `image`/`video`/`assignment`/`homework`) show it's a read-receipt tracker — whether a parent/student has viewed a piece of posted content.
- **Impact:** low severity (not a bug), but a real cost to anyone new investigating the codebase — this is exactly the kind of naming collision the audit process exists to catch before it gets carried into SchoolOS.
- **SchoolOS action:** name tables for what they store; don't reuse a domain-sounding name for an unrelated technical mechanism.

## F20 — `Api\AttendanceController::index($student_id)` — IDOR, zero ownership check on caller-supplied student ID — CONFIRMED
- **File:** `app/Http/Controllers/Api/AttendanceController.php`, `index($student_id)`
- **Root cause:** the method takes `$student_id` directly from the route and uses it unfiltered: `Attendance::where([['school_id', Auth::user()->school_id], ['academic_year_id', $academic_year->id], ['user_id', $student_id]])->get()`. The only scoping applied anywhere in the method is `school_id` (tenant-level, via the authenticated caller). There is no check that `$student_id` belongs to the authenticated caller (student self-access) or is one of the caller's linked children (parent access) — `student_parent_links` is never queried.
- **Impact:** any authenticated parent or student can read any other student's attendance records and computed attendance percentage within the same school by supplying an arbitrary `$student_id` — a textbook IDOR. This sits in the same shared parent/student API surface as `Api\ChildrenController`, which is called out below as the counter-example proving the fix isn't hypothetical.
- **Contrast — positive pattern found two files over:** `Api\ChildrenController::showChildren($id)` does the correct thing: it explicitly intersects the requested `$id` against the caller's own linked-children data (via `student_parent_links`) before returning anything, rather than trusting `$id` alone. Same domain, same shape of risk, handled correctly here and not in `AttendanceController`.
- **Open items carried from domain-map review:** `Api\FeesController`, `Api\MarksController`, `Api\TimetableController`, `Api\LeaveController` (the other parent-facing views of a specific student's data) have not yet been individually audited for this same ownership-check gap — given F20 was found in the very next controller over from the one that does it correctly, these should be treated as suspect until checked, not assumed safe.
- **SchoolOS action:** every "fetch a specific [child/student]'s data" endpoint must intersect the requested ID against the caller's own relationship data before querying — `ChildrenController::showChildren()` is the in-codebase template to standardize on, not a one-off. See `12-schoolos-architecture.md` §3a.

## F21 — `TeacherLeaveApplication` surface has zero scoping anywhere — no tenant check, no relationship check, on read, write, or approve — CONFIRMED, worse than F20
- **Files:** `app/Http/Controllers/Api/LeaveController.php` (`show`, `update` — parent/student-facing), `app/Http/Controllers/Api/Teacher/LeaveController.php` (`show`, `update`, `destroy` — teacher's own leave), `app/Http/Controllers/Api/Teacher/StudentLeaveController.php` (`approveStore`, `rejectStore` — teacher approving a student's leave).
- **Root cause:** every one of these methods does `TeacherLeaveApplication::where('id', $id)->first()` and nothing else — no `school_id` filter, no ownership/relationship check of any kind. This is a strictly worse pattern than F20 (which at least scopes by `school_id`): here a caller from **any school** can read, edit, cancel, approve, or reject **any** leave application in the entire application by guessing/incrementing `$id`.
- **Impact:** cross-tenant read (leave reason, remarks, dates — arguably sensitive) and cross-tenant write: `update()` lets any authenticated user overwrite another user's pending leave request; `destroy()` lets any teacher cancel another teacher's leave; `approveStore()`/`rejectStore()` let any teacher approve or reject any student's leave application school-wide or cross-school, notifying the wrong parent/teacher pair in the process (`$leave->user_id` is trusted for downstream notification lookups too). This is the same shared `TeacherLeaveApplication` table serving both teacher self-service leave and student leave approval, so the blast radius spans both domains.
- **SchoolOS action:** this is the clearest possible case for §3a's `relationshipScope` being mandatory, not optional, on every single-record fetch/mutate — `tenantScope` alone (which F20 at least had) is still not present here at all. No endpoint should resolve a record by bare `id` without both checks.

## F22 — `Api\Teacher\AssignmentController` and `HomeworkController`'s `show`/`update`/`edit` have no check at all — the sibling `destroy` methods do, confirming this is an inconsistency within the same controller, not a design choice
- **Files:** `app/Http/Controllers/Api/Teacher/AssignmentController.php` (`show`, `update` — `destroy` has no check either, all three unscoped), `app/Http/Controllers/Api/Teacher/HomeworkController.php` (`show`, `edit`, `update` — contrast with `destroy`, which correctly calls `Gate::allows('homework', $homework)`, i.e. F18's tenant-only check).
- **Root cause:** `Assignment::where('id',$id)->first()` / `Homework::where('id',$id)->first()` with zero authorization check of any kind on the read and update paths. `HomeworkController::destroy` proves the developers knew a check belonged here (`\Gate::allows('homework', $homework)`) — they simply didn't apply it consistently to the sibling methods on the same resource.
- **Impact:** any authenticated teacher, in any school, can view or overwrite any assignment or homework record in the system by ID — full content substitution (title, description, dates, attachment) on someone else's assignment, with no tenant check let alone the class/subject-assignment check F18 already flags as missing even where a Gate does run.
- **SchoolOS action:** reinforces §3a's lint/test proposal — a per-resource authorization check that exists on one CRUD method but not its siblings is exactly the failure mode an automated "every ID-resolving endpoint has a registered scope check" test is meant to catch. Manual per-controller diligence already failed here once (`destroy` remembered, `show`/`update` didn't).

## F23 — `Api\EventGalleryController::showimage($event_id)` bypasses the class-targeting segmentation the list endpoint enforces
- **Files:** `app/Http/Controllers/Api/EventGalleryController.php` (`showimage`), contrast with `app/Http/Controllers/Api/EventsController.php` (event listing methods).
- **Root cause:** `EventsController`'s listing methods correctly filter by `select_type`: `'school'`-type events are visible school-wide, but `'class'`-type events are additionally filtered to `standard_id = $student->studentAcademicLatest->standardLink_id` — i.e., only the requesting student's own class sees class-targeted events. `EventGalleryController::showimage($event_id)` fetches a single event by ID with only a `school_id` filter — `select_type`/`standard_id` are never checked.
- **Impact:** a parent or student can view a class-targeted event (and, per the method's evident intent, its gallery images) for a class that isn't theirs, bypassing the exact segmentation the listing endpoint enforces one file over. Lower sensitivity than F18/F20/F21/F22 (event/gallery content, not personal student records) but the same shape: a single-record fetch skips a check its own list-endpoint sibling performs.
- **Separate, non-security note:** the method's actual `EventGallery`-querying logic is commented out in the reviewed source — what's returned is the parent `Events` record's own fields (`ShowEventResource`), not gallery images. The method likely doesn't do what its name implies; flagged as probably-incomplete/dead code, not a new security finding.
- **SchoolOS action:** the class-vs-school segmentation (`select_type`) should be enforced as part of `ScopeService.relationshipScope` for *any* endpoint touching a `class`-targeted event, single-record fetches included — not just re-implemented per-listing-endpoint the way GegoK12 has it.

## F24 — `NoticeBoard` single-record fetch is fully unscoped (both parent and teacher surfaces); teacher-side list endpoint also accepts a caller-supplied teacher ID instead of using the caller's own identity
- **Files:** `app/Http/Controllers/Api/NoticeBoardController.php` (`show`), `app/Http/Controllers/Api/Teacher/NoticeBoardController.php` (`show`, `showNotices`).
- **Root cause (both `show` methods):** `NoticeBoard::where('id',$id)->where('type', ...)->get()` — no `school_id` filter at all on either the parent-facing or teacher-facing `show`. Same zero-scoping tier as F21/F22.
- **Root cause (`showNotices($teacher_id)`):** takes `$teacher_id` as a route parameter and resolves that teacher's `teacherlink` assignments to decide which notices to return, rather than using `Auth::id()`. No check that `$teacher_id` is the authenticated caller.
- **Impact:** any authenticated user in any school can read any notice by ID (`show`, both surfaces) — cross-tenant disclosure of notice-board content. Separately, any teacher can view another teacher's class-notice list by supplying their ID (`showNotices`) — a horizontal information-disclosure gap, lower severity than the `show` methods but the same underlying mistake (trusting a route-supplied identity instead of the session's).
- **Also observed, non-security:** `Api\Teacher\NoticeBoardController::show` filters with `->where('type','==','teacher')` — `'=='` is not a valid SQL comparison operator; this is very likely a hard query error on every call, independent of the scoping gap. Flagged for completeness, not logged as a separate finding.
- **SchoolOS action:** no endpoint should ever accept an identity parameter (`$teacher_id`, `$student_id` used as "who is asking") when the value should always be the authenticated caller — use `Auth::id()` directly and drop the parameter. Combined with §3a's mandatory `tenantScope`+`relationshipScope` on every ID-resolving fetch, this closes both gaps structurally rather than per-endpoint.

## F25 — `Api\TaskController`: read, update, and destroy paths have zero scoping — including an unscoped delete and an unscoped bulk-ID write — the most severe single controller found in this audit
- **File:** `app/Http/Controllers/Api/TaskController.php` — `show`, `edit`, `update`, `snooze`, `destroy`, `changestatus`.
- **Root cause:** every one of these resolves `Task::where('id', $id)->first()` (or, in `changestatus`, iterates a client-supplied `$request->task_completed` array of IDs) with **no `school_id` filter and no ownership/assignee check of any kind**. Contrast with this controller's own list methods (`myActiveList`, etc.), which at least apply `school_id`+`academic_year_id` — the single-record and mutating methods don't even do that much.
- **Impact — broader than a read-only IDOR:**
  - `show`/`edit`: cross-tenant read of any task's title, to-do content, and reminder details by ID.
  - `update`/`snooze`: cross-tenant write — a caller can modify a task and its assignee record for any `$id`, in any school, with no verification.
  - **`destroy($id)`: cross-tenant delete** — any authenticated user can delete any task (and its `TaskAssignee` rows) in any school.
  - **`changestatus()`: unscoped bulk write** — the request body directly supplies which task IDs to mark complete, with no per-ID ownership check, so a single call can silently mark other users' tasks (any school) as done.
- **SchoolOS action:** this is the strongest existing evidence for treating destructive operations (`destroy`, bulk status changes) as requiring the *same* mandatory `tenantScope`+`relationshipScope` check as reads — GegoK12 shows these are, if anything, more likely to be left unscoped than read paths, not less. `12-schoolos-architecture.md` §3a's proposed lint/test rule should explicitly include delete and bulk-mutation endpoints, not just single-record fetches.

## F26 — `Api\LessonPlanController`: `print` and `show` fully unscoped; `index`/`subjectIndex` are the same tenant-only shape as F20
- **File:** `app/Http/Controllers/Api/LessonPlanController.php` — `print($id)`, `show($id)`, `index($student_id)`, `subjectIndex($student_id,$subject_id)`.
- **Root cause (`show`, `print`):** both do `LessonPlan::where('id',$id)` with **no `school_id` filter at all** — same zero-scoping tier as F21/F22/F24/F25. `print()` additionally renders the fetched (unverified) lesson plan to PDF, writes it to `{caller's own school slug}/lessonplan/{title}_{class}.pdf` in storage, and returns the file path — so an unrelated school's lesson-plan content gets written into the caller's own school's storage folder as a side effect of the IDOR, not just returned in the response body.
- **Root cause (`index`, `subjectIndex`):** `$student_id` is resolved via `User::where('id',$student_id)->first()` with no ownership check, then used to look up `standardLink_id` for a `Teacherlink` query scoped only by the caller's own `school_id`/`academic_year_id` — the same tenant-only-not-relationship-scoped pattern `10-api-map.md` §2 generalized as F20's shape. `$student` is also dereferenced (`->studentAcademicLatest->standardLink_id`) with no null check, so a nonexistent or wrong-tenant `$student_id` throws rather than failing cleanly.
- **Impact:** cross-tenant read of lesson plan content by ID (`show`), plus an unintended cross-tenant file write into the caller's own storage (`print`); within-tenant IDOR letting a parent/student view another student's class lesson plans by ID (`index`/`subjectIndex`).
- **SchoolOS action:** same as F20/F21 — `relationshipScope` mandatory on every single-record and student-scoped fetch; `print`'s file-write side effect is a good concrete argument for gating *before* any side-effecting work runs, not just before the response is built.

## F27 — `Api\FeedbackController`: `notifications($id)` is a tenant-only IDOR on arbitrary users; `store()` lets a caller file feedback under any student ID
- **File:** `app/Http/Controllers/Api/FeedbackController.php` — `notifications($id)`, `store()`. (`index`, `sentMessages`, `readMessage` are all correctly scoped to `Auth::id()` — noted as further examples of the identity-from-session pattern already used as the SchoolOS template.)
- **Root cause (`notifications`):** `User::where('school_id',$school_id)->where('id',$id)->first()` — tenant-scoped but not caller-scoped; any authenticated user can pull any other user's notification feed (`notifiable_id = $id`) within the same school just by knowing/guessing their user ID.
- **Root cause (`store`):** `$feedback->student_id = $student_id` is taken directly from the route with no check that `$student_id` is the caller's own child — the same identity-spoofing-on-write shape `10-api-map.md` §2 already flagged for `HomeworkController::store`/`AssignmentController::store`/`LeaveController::store`. A parent can submit feedback attributed to a student who isn't theirs.
- **Impact:** within-tenant disclosure of another user's notification history (`notifications`); identity spoofing on a written record (`store`) — lower sensitivity than the homework/assignment/leave write-spoofing cases, but the same root cause recurring a fourth time.
- **SchoolOS action:** reinforces `12-schoolos-architecture.md` §3a — `relationshipScope` needs to apply to `notifiable_id`-style lookups too, not just the student-record endpoints already covered; the recurring write-spoofing pattern (now four controllers) is strong evidence this needs to be structural, not remembered per `store()` method.

## F28 — `Api\Search\UserSearchController`: unauthenticated-shaped, fully cross-tenant user enumeration by name substring
- **File:** `app/Http/Controllers/Api/Search/UserSearchController.php`, `index()`.
- **Root cause:** `User::where('name', 'LIKE', '%'.Str::lower($q).'%')->get(['id','name'])` — no `school_id` filter, no relationship check, not even the tenant-only floor every other finding in this log at least has. The only gate is that the route presumably sits behind the `api` middleware group (session/token required to reach it at all — not independently re-verified this pass, see `10-api-map.md`'s route-level caveat), but the query itself applies zero scoping once authenticated.
- **Impact:** any authenticated user, in any school, can enumerate `id`+`name` for every user in the **entire application across all schools** via substring search — a full cross-tenant PII enumeration surface, worse in kind than every other finding in this log (which are all bounded to IDOR-by-guessable-ID within or across one relationship); this is bulk, queryable, cross-tenant-by-design. Plausible use: building a target list of valid user IDs to feed into F20/F21/F24/F25/F26's unscoped-`$id` endpoints — this controller is a force-multiplier for every ID-guessing finding above it.
- **SchoolOS action:** any search-by-name endpoint must be `tenantScope`d at minimum (same school as caller) and ideally `relationshipScope`d further (e.g., parents search only their own children's class rosters, teachers only their assigned classes) — never a bare unscoped `LIKE` across the whole `users` table. Given F28's role as an enumeration feeder for the ID-based findings, this should be treated as comparably high priority to F21/F25 despite being "just a search," not deprioritized as a lesser finding.

## F29 — `Api\Teacher\StudentAssignmentController`: any teacher can write grades onto any student's submission, any school — zero scoping on the entire controller
- **File:** `app/Http/Controllers/Api/Teacher/StudentAssignmentController.php` — `submittedAssignmentList`, `completedAssignmentList`, `store`, `show`, `update` (i.e., every method in the controller).
- **Root cause:** every method resolves `StudentAssignment::where('id',$id)->first()` (or `where('assignment_id',$assignment_id)` for the two list methods) with no `school_id` filter and no check that the assignment belongs to a class/subject the authenticated teacher actually teaches (`Teacherlink`) — not even the tenant-only floor most other findings in this log have.
- **Impact:** this is the controller where a teacher grades a student's assignment submission (`obtained_marks`, `comments`). `store()`/`update()` let **any authenticated teacher, in any school**, set the marks and comments on **any student's submission** in the entire application by guessing/incrementing `$id` — a grade-integrity write, not just a read-IDOR. `show()` discloses another student's marks/comments the same way. This is a materially different risk class from the read-only findings above: it's forged academic records, not just disclosed ones.
- **SchoolOS action:** grading endpoints need both `tenantScope` and a `Teacherlink`-based `relationshipScope` (the requesting teacher must be linked to the assignment's `standardLink_id`+`subject_id`) enforced structurally before any write — this is arguably the highest-stakes write-path gap found in the audit so far, since its blast radius is falsified grades, not just exposed data.

## F30 — `Api\Teacher\LessonPlanController`: `approve`/`reject` have no scoping *and* no role check — any teacher can approve/reject any lesson plan, bypassing the principal-only distinction the controller's own `index()` establishes
- **File:** `app/Http/Controllers/Api/Teacher/LessonPlanController.php` — `approve($id)`, `reject($id)`, `show($id)`, `print($id)`, `updateStepOne($id)`.
- **Root cause:** `index()` in this same controller explicitly branches on `Auth::user()->hasRole('principal')` to decide whether to show all lesson plans (principal view) or just the caller's own (teacher view) — i.e., the codebase clearly treats principal-only visibility as a real distinction elsewhere in this file. `approve()` and `reject()`, the two methods that actually change a lesson plan's approval status, check **neither** a role (`hasRole('principal')`) **nor** any tenant/ownership scoping (`LessonPlan::where('id',$id)->first()` with nothing else) — a `status = 'approved'`/`'rejected'` write plus a `LessonPlanApproval` audit row is made available to literally any authenticated teacher, for literally any lesson plan by ID, in any school.
- **Impact:** any teacher can rubber-stamp (or reject) their own or a colleague's lesson plan without principal review — a workflow-integrity bypass, not just data exposure — and can do so cross-tenant against another school's lesson plans given a guessable `$id`. `show`/`print`/`updateStepOne` add the same unscoped-read/unscoped-write pattern already established for the parent-facing `Api\LessonPlanController` (F26) to the teacher-facing controller too.
- **SchoolOS action:** approval-workflow endpoints need the role check enforced at the same structural layer as tenant/relationship scoping — `index()`'s inline `hasRole('principal')` branch shows the codebase *has* the primitive to check this, it's simply not applied to the two methods where it matters most (the actual state-changing approval actions). This is the same "developer remembered the check in one method, not its siblings" failure mode as F22/F24, now found a third time.

## F31 — Every approval controller in the codebase shares F30's gap: `approve`/`reject` (and one `update` bulk variant) have zero tenant scoping and zero role check, across all five controllers that implement this workflow
- **Files, all confirmed independently, identical root cause in each:**
  - `app/Http/Controllers/Api/Teacher/Approval/AssignmentApprovalController.php` (`approve`, `reject`)
  - `app/Http/Controllers/Api/Teacher/Approval/HomeworkApprovalController.php` (`approve`, `reject`) — `approve()` additionally flips `Homework::status` to `'publish'` and fans out class-wide parent notifications as a side effect
  - `app/Http/Controllers/Teacher/Approval/AssignmentApprovalController.php` (`approve`, `reject`) — web equivalent, same body
  - `app/Http/Controllers/Teacher/Approval/HomeWorkApprovalController.php` (`approve`, `reject`) — web equivalent, same body, same publish+notify side effect
  - `app/Http/Controllers/Admin/Approval/HomeworkApprovalController.php` (`approve`, `reject`, **and** `update()` — a bulk variant that loops a client-supplied `$request->approvallist` array of homework IDs through `approve`/`reject` with no per-ID check either)
- **Root cause:** every `approve`/`reject` method resolves its target purely by the route/body-supplied `$id` — `AssignmentApproval::where('assignment_id',$id)->first()` or `HomeworkApproval::where('homework_id',$id)->first()` — with no `school_id` filter and no role check (`hasRole('principal')` or equivalent), despite `Api\Teacher\LessonPlanController::index()` (§4 of `15-academic-domain-map.md`) proving the codebase has and uses that exact role-check primitive elsewhere. This is F30's pattern, now confirmed systemic: it is not a one-off in the lesson-plan controller, it is the default shape of *every* approval workflow in the application, teacher-facing, web, and admin-facing alike.
- **Impact:** any authenticated teacher (not just a principal) can approve or reject any homework or assignment's approval record, in any school, by ID — including the `Admin`-namespace controller, where the same unscoped lookup means an admin from one school can act on another school's approval records purely because the endpoint never checks `school_id`. The `Homework` approve path is the highest-impact instance: approving fires the actual publish-and-notify pipeline (parents get "New Homework Added" pushes/SMS) for content the approver may have no relationship to at all. The `Admin` controller's `update()` bulk method compounds this — a single request can silently approve/reject an attacker-chosen list of homework IDs school-wide.
- **SchoolOS action:** this closes the open item `15-academic-domain-map.md` flagged as "worth prioritizing next" — the prediction held 5 for 5. Confirms `12-schoolos-architecture.md` §3a's proposed lint/test rule needs to explicitly enumerate *every* approval/publish-workflow endpoint as a mandatory `tenantScope` + role-based `relationshipScope` target, not just single-record student/homework/assignment fetches — approval actions are state-changing and notification-triggering, arguably higher-stakes than the plain CRUD gaps found elsewhere, and this pass shows they were *uniformly* missed across five independent implementations of the same workflow (API and web, teacher- and admin-facing) rather than inconsistently, unlike F22/F24's "one method forgot it" shape.
