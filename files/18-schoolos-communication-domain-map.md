# 18 — SchoolOS Communication Domain Map (Phase 5 pre-schema pass): Notifications, Announcements, Parent Communication

**Status:** This is the domain-map pass `14-schoolos-implementation-plan.md` §5/§8 requires before Phase 5 schema/implementation work — same posture as `17`'s pass for Phase 4: design, not further reverse-engineering, since the reference-codebase findings this phase draws on (`09-attendance-map.md` §5, F24, F27) are already captured. No schema, migration, or controller code is written *by this pass*. **However, §2 below is not optional reading**: a materially complete draft of this phase's models, migrations, repositories, controllers, events, and listeners was found already sitting in the repository, built without this domain-map pass having happened yet. This document evaluates that code against the model it derives independently, rather than assuming it's correct because it exists.

---

## 1. What this phase inherits, already resolved

- **The attendance fan-out is a template, not a redesign target** (`14` §5, `09` §5). GegoK12's real-time per-parent notification-on-absence is confirmed a genuinely good pattern in `09` §5 — the only correction `09` §6 and `12` §5 make is to decouple it from the attendance-write transaction (a domain event with a separate listener, not inline `foreach ($student->parents)` dispatch inside the same loop that writes the row). Phase 3's build already anticipated this exactly: `AttendanceRepository` dispatches `AttendanceMarked`/`AttendanceCorrected` *after* the write commits, and both event classes' own doc comments say, in effect, "no listener is wired yet — that's Phase 5's job." This phase's attendance-notification work is therefore just writing the listener, not redesigning the write path.
- **`content_read_receipts` belongs to this phase's data model, confirmed** (`13` §6). `13` §6 is explicit that GegoK12's `student_history` — renamed for what it actually does — is "a general read-receipt tracker for any posted content type, attendance included only incidentally." Nothing about its `entity_type` enum (`image`, `video`, `assignment`, `homework`) is attendance-specific, and nothing in `13` ties its ownership to Phase 3. It belongs here.
- **`ScopeService`'s generic column-based dispatch already covers the common case, for free** (same shape `17` §1 found for Phase 4). `relationshipScope()`'s existing `class_section_id` branches (teacher/parent/student) and `student_id` branches need no new code for any entity below that carries one of those two columns — confirmed by reading `ScopeService.php` directly, not assumed by analogy.

## 2. A partial Phase 5 implementation already exists in the repository — ahead of, and outside, this domain-map pass

Before working out the entity list from scratch, the repository was checked for existing Communication-domain code, the same way `17`'s pass checked what Phase 2's `Subject` model had already resolved. What turned up is bigger than a resolved dependency: **most of Phase 5's build already exists on disk**, timestamped *before* the current Phase 4 files, with every new file's doc comment citing `14 §5` as its design ref — i.e., it was written as if it were this phase's implementation, not a false positive from an unrelated feature.

**What's there:**
- `Announcement` model + migration (`audience_type` enum `school`/`class_section`, `class_section_id` nullable) + `AnnouncementRepository` (single write path, role + section-assignment validation, `visibleTo()` read query) + four portal controllers (Admin store-only, Teacher index+store, Parent/Student index-only) + `AnnouncementPublished` event.
- Laravel's standard `notifications` table (not a bespoke one) + `NotifyAudienceOfAnnouncement` listener + `AnnouncementPublishedNotification` + `NotifyParentsOfAbsence` listener (reacting to `AttendanceMarked`, exactly closing the §1 item above) + `AttendanceAbsenceNotification` + a shared `HasNotificationInbox` trait used by all three portals' `NotificationController` classes.
- `content_read_receipts` migration + `ContentReadReceipt` model, with `'announcement'` **already added** to the `entity_type` enum `13` §6 specified — i.e., whoever built this had already made the exact call this pass's §3 below makes independently.

**What was checked, and what's actually missing:**
- **Nothing is wired.** `AppServiceProvider::boot()` is empty — `NotifyAudienceOfAnnouncement` and `NotifyParentsOfAbsence` are registered against nothing, despite `NotifyAudienceOfAnnouncement`'s own doc comment asserting it's "registered against `AnnouncementPublished` in `AppServiceProvider::boot()`." That registration does not exist in the file. Confirmed by reading the file directly.
- **No routes.** `routes/web.php` has zero route entries for any Announcement or Notification controller — the only occurrence of "announcements" in that file is a doc comment for the *parent dashboard* group listing it as a future addition. None of these controllers are reachable today.
- **Zero test coverage.** No `Phase5TestGateTest`, no `AnnouncementControllerTest`, no `NotificationControllerTest` anywhere in `tests/`. Confirmed by directory search, not inferred from absence in a listing.
- **No decision-register entry.** `16-schoolos-decisions-register.md` has no line about Phase 5 being started early, unlike every other deliberate scope decision in this project (D1–D5, the parent-dashboard call, the exams-core call). This looks like a stray build pass that ran ahead of the phase sequencing `14` establishes, not a decision anyone signed off on.

**Assessment (checked against §3–§6 below, not assumed):** the code that exists is good and matches the model this pass derives independently — `Announcement`'s `class_section_id` dispatches through `ScopeService`'s existing generic branch with no changes needed to that class (confirmed by reading `ScopeService.php`); the notification inbox is self-scoped via Laravel's own `Notifiable` relation rather than a route-supplied ID, which is F27's fix by construction, not by review; the attendance/announcement fan-outs are dispatched after their respective writes commit, matching `12` §5's decouple-from-the-transaction guidance. It is not a case of "this needs to be thrown out." But it was built without going through the gate `14` §8 explicitly requires before Phase 5 schema/implementation work starts, it has no tests, and its own doc comments describe wiring that isn't real — which is precisely the situation a domain-map-first, test-gated process exists to prevent. **This pass's recommendation:** treat the existing code as a strong first draft the next session should build *from*, not as already-shipped Phase 5 work — it still needs the wiring in §8's open items, the one missing entity in §3 below, and the full test gate in §6 before it's real, and it should get a `16`-style decision-register line noting it was found mid-flight and folded into the normal process rather than reverted, so this doesn't look like an unexplained gap to the next person reading the register.

## 3. Entities this phase needs

`14` §5's build line names three things — notifications, announcements, parent communication — and the existing code (§2) covers the first two plus the read-receipt tracker `13` §6 requires. It does not cover the third as its own entity.

| Entity | Carries | Status |
|---|---|---|
| `Announcement` | `class_section_id` (nullable — null means school-wide) | Already built (§2); matches the model below |
| `DatabaseNotification` (Laravel's own `notifications` table) | `notifiable_id`/`notifiable_type` | Already built (§2); matches the model below |
| `ContentReadReceipt` | `user_id`, `entity_type`/`entity_id` | Schema/model already built (§2); write path (mark-as-read) not built — correctly deferred by its own migration's doc comment, not an oversight |
| `Feedback` (parent-communication) — **new, not yet built** | `student_id` | Not present anywhere in the repository |

**Why `Feedback` is a fourth entity, not a variant of `Announcement`:** `Announcement` is one-way, staff-authored, broadcast content. `14` §5's "parent communication" is the reference codebase's `Api\FeedbackController` — a parent-initiated message tied to a specific student, with `index`/`sentMessages`/`readMessage` (correctly `Auth::id()`-scoped in the reference already, per F27's own text) and `notifications($id)`/`store()` (the two gaps F27 found: a tenant-only IDOR reading another user's notification feed, and an unchecked `student_id` on write letting a parent file feedback under a child that isn't theirs). Nothing in `Announcement`'s shape — authored by staff, visible to a computed audience — covers a parent writing to the school about their own child. Collapsing the two into one table would force `Announcement` to carry a `student_id` column it has no other use for, the same reasoning `17` §2 gave for keeping `Assignment`/`AssignmentSubmission` separate rather than merging them.

## 4. Scope model per entity

| Entity | Teacher sees | Parent/student sees | Admin (`school_admin`) sees | Scoping mechanism |
|---|---|---|---|---|
| `Announcement` | School-wide rows + `class_section` rows for sections they're assigned to | School-wide rows + `class_section` rows for own/linked children's sections | Whole school (default branch) | Generic `class_section_id` dispatch for the `class_section` half; `tenantScope`-only, no relationship narrowing, for the `school`-wide half — **two query branches merged, not one**, since a null `class_section_id` would otherwise fall through `relationshipScope()`'s final deny-by-default case (confirmed in `ScopeService.php`) |
| `DatabaseNotification` | Own inbox only | Own inbox only | Own inbox only | **Not `ScopeService` at all** — `$user->notifications()` is Laravel's `Notifiable` relation, inherently constrained to `notifiable_id = $this authenticated user's id`; there is no by-ID route parameter for any role to misuse, which is F27's `notifications($id)` fix by removing the vulnerable shape rather than adding a check to it |
| `ContentReadReceipt` | Own receipts only (read); write requires relationship access to the underlying entity (see §5) | Own receipts only (read); same write requirement | Whole school (default branch, if an admin view of read-receipts is ever built — not currently planned) | Self-scoped by `user_id` for reads (same non-`ScopeService` shape as notifications); the *write* path needs `relationshipScope()` run against the underlying `entity_type`/`entity_id`, not against the receipt row itself — see §5 |
| `Feedback` (new) | N/A — not a teacher-authored resource; a teacher reading feedback filed about their own class is a real future need but is not decided by this pass (see §8) | Own/linked children's feedback (`student_id` dispatch) | Whole school (default branch) | Generic `student_id` dispatch for parent/student reads — **no new `ScopeService` code**, same as `AssignmentSubmission`'s read side in `17`; the write path still needs its own check (§5), the same lesson `17` §5 already drew for grading writes |

**The two rows that aren't a plain "no new code" story are `Announcement` (two merged branches, not a `relationshipScope()` gap — already correctly handled by `AnnouncementRepository::visibleTo()`) and `Feedback`'s write path (a generic-dispatch read paired with a write check that dispatch alone doesn't provide, the exact shape `17` §3 established for `AssignmentSubmission`/`ExamMark`).** `DatabaseNotification` and `ContentReadReceipt`'s read side are the one genuinely new shape this phase introduces: self-scoped-by-identity, no tenant or relationship question to ask at all, because the row's own foreign key already *is* the caller. That's a third scoping shape alongside `tenantScope`/`relationshipScope`, worth naming explicitly rather than leaving implicit — a future reviewer checking "does every by-ID endpoint have a `relationshipScope` check" needs to know these controllers are correctly exempt, not silently missed.

## 5. Role-based scope widening: does Phase 5 need it?

Same check `17` §4 ran for Phase 4, against the same role vocabulary (`RoleSeeder`: `super_admin`, `school_admin`, `teacher`, `student`, `parent`, `accountant`, `librarian`, `receptionist`, `staff`).

**Finding: no, for the same reason `17` §4 found.** `school_admin` already gets full within-tenant visibility on `Announcement` and (once built) `Feedback` via `relationshipScope()`'s existing default branch — there's nothing to widen. `$wideVisibilityRoles` stays unused by this phase too.

**One real question this phase surfaces that Phase 4 didn't:** `AnnouncementAudienceResolver`'s `'school'`-wide audience (already built, §2) notifies `teacher`/`parent`/`student` and deliberately excludes `accountant`/`librarian`/`receptionist`/`staff`. This wasn't decided anywhere in `14`, `13`, or `16` — it's a design choice embedded in code that was written outside the normal process (§2). It may well be the right call (a school-wide announcement about, say, a snow closure plausibly should reach non-teaching staff too), but per `16`'s own pattern for the parent-dashboard and exams-core-vs-addon questions, this deserves an explicit yes/no in the decision register rather than a silent default that happened to already be written.

## 6. Write-path scoping requirements

Same discipline as `12` §3a and `17` §5: every write, not just every read, goes through the shared mechanism — never a per-controller ad hoc check.

| Write path | Must check | Closes / status |
|---|---|---|
| Create `Announcement` | Role check (`school_admin` may post either audience type; `teacher` may only post `class_section`, and only for a section they're assigned to, via the same `AssertsTeacherAssignedToSection` check `LessonPlan`/`Assignment`/`Exam`/`Timetable` repositories already use) | Already built correctly (§2) — `AnnouncementRepository::create()` |
| Fan out `AnnouncementPublished` to its computed audience | Dispatched only after the row commits, via a separate listener — not inline in the write path | Already built correctly (§2), but **the listener is not registered anywhere** — see §8 |
| Fan out `AttendanceMarked(absent)` to linked parents | Same decouple-from-write-transaction shape, closing `09` §5/§6's specific finding | Already built correctly (§2), same registration gap as above |
| Fetch a notification inbox | Must never accept a `notifiable`/user-id route parameter — always resolve from the authenticated session | Already built correctly (§2) — closes F27's `notifications($id)` IDOR and generalizes F24's `showNotices($teacher_id)` lesson (never trust a route-supplied identity when the session already has it) |
| Create `Feedback` | The submitted `student_id` must be validated against the caller's own linked children (parent) or the caller's own id (student), before any write — same "reject loudly before any transaction opens" posture `AnnouncementRepository::create()` already uses | **Not built** — closes F27's `store()` spoofing gap |
| Mark a `ContentReadReceipt` (once the endpoint exists) | The caller must already have `relationshipScope()`-visible access to the underlying `entity_type`/`entity_id` before a read-receipt for it can be recorded — a receipt is proof the caller saw something they were allowed to see, not a free-standing fact | **Not built** — schema/model exist; this requirement should be recorded now (per this document's whole purpose) so it isn't rediscovered as a gap after the endpoint ships |

## 7. Test gate

Same shape as Phase 1/3/4's gates, extended to this phase's four resource types — and, unusually, doubling as the regression suite the already-written code in §2 currently has none of.

| Test | Regresses / confirms |
|---|---|
| A user with no `class_teacher_assignments`/enrollment tie to a `class_section` cannot see that section's `class_section`-audience announcements; every in-tenant user sees `school`-wide ones regardless | Generalizes F24 (`NoticeBoard` fully-unscoped `show`); confirms `AnnouncementRepository::visibleTo()`'s two-branch merge actually works under real data, not just reasoned about |
| No endpoint returns another user's notification inbox by ID — every notification route resolves strictly from the authenticated session | **F27** (`notifications($id)`), generalizing F24's `showNotices($teacher_id)` lesson to this domain |
| A parent cannot file `Feedback` under a student who isn't their own linked child; a student cannot file it as another student | **F27** (`store()` spoofing) |
| `AnnouncementPublished` and `AttendanceMarked(absent)` each notify exactly their resolved audience — no more, no fewer — and the fan-out cannot affect the outcome of the write it follows (a failing/slow notification send doesn't roll back or block the write) | Confirms `09` §5/§6's decouple-from-the-transaction guidance holds in the built system |
| A `content_read_receipts` write is rejected if the caller has no `relationshipScope`-visible access to the target `entity_type`/`entity_id` | New coverage — closes the gap named in §6 before any code depending on it ships |
| Every current-and-future "fetch/act on a specific announcement/feedback by ID" endpoint carries the `scope.checked` route marker `Phase1TestGateTest`'s lint already enforces for Phase 1/4 | F22, extended — not yet applicable to `Announcement` (no by-ID endpoint exists yet, see §8) but binding the moment one is added |
| `NotifyAudienceOfAnnouncement` and `NotifyParentsOfAbsence` actually fire on their respective events in the running application, not just when invoked directly in a unit test | New coverage — directly targets the registration gap §2/§8 found; a listener class existing is not evidence it's wired |
